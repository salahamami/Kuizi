# 0009. Learner event contracts: Avro, one topic per event, BACKWARD_TRANSITIVE

- Status: Proposed (the product owner accepts it by merging T023)
- Date: 2026-10-18
- Ticket: T023 (KK-43), Data Engineering agent
- Catalogue: [`docs/data/event-catalogue.md`](../../data/event-catalogue.md) · sources: [`schemas/events/`](../../../schemas/events/) · tooling: [`schemas/README.md`](../../../schemas/README.md)

## Context

Every answer, hesitation, hint, tutor message, Focus session and notification becomes an event on the Kafka API (Redpanda locally, Amazon MSK later, ADR 0006). Many services read them: real-time aggregation (T026), the warehouse (T027, T028), the online sequence builder (T048), knowledge-tracing training (T041, T042, T148), the Notification Orchestrator (T152) and its metrics (T161), analytics (T191) and erasure (T018). Producers are the apps (through the telemetry SDK, T024, and ingestion, T025) and a few servers (answer evaluation, T221; the tutor; the orchestrator). Those parties change at different times, so the contracts need a format with a registry, rules for evolving them without breaking anyone, and rules for personal data: most learners are minors, and an accommodation can reveal a disability (Law 2004-63, [requirements section 3](../../requirements/accessibility-focus-notifications.md)).

## Decision

1. **Avro with the schema registry.** The ticket allowed Avro or Protobuf. Avro is chosen because its evolution rules rest on field defaults that the registry checks, the Snowflake Kafka connector (T027) and Kafka Connect read it natively with the registry, Redpanda's registry supports it, and its JSON form is readable when debugging. Protobuf's generated code is nicer in TypeScript, but its compatibility depends on field numbers and has no defaults to fall back on.
2. **One topic per event: `learner.<event>.v<major>`**, for example `learner.item.answered.v1`. Registry subjects follow the topic name strategy, `<topic>-value`, the default of every client and connector. The message key is `envelope.student_id` as a plain string, so one learner's events stay in order within a topic.
   - Rejected: *one topic for all learner events* (record name strategy). It keeps the order across event types, but every consumer would read every event, sensitive fields included, and retention, access control and warehouse tables could not differ per event. Cross-event order is not needed: `item.answered` carries everything knowledge tracing uses, and `presentation_id` and `session_seq` let the warehouse join and order the rest.
   - Rejected: *one topic per domain* (items, sessions, notifications): a middle ground that keeps the access-control problem inside each topic.
3. **Self-contained schemas.** Shared types (`Envelope`, `ItemContext`, `AccommodationContext`, enums) are written once in `schemas/events/common/` and inlined into each event schema before it is checked or registered. Registry schema references are not used: every client library and the connector read a self-contained schema without extra lookups.
4. **Compatibility BACKWARD_TRANSITIVE on every subject.** A new schema must read data written with every earlier version, not only the last one: Kafka keeps days of events, the warehouse keeps months, and replays (T031) read old data with today's schema. Plain BACKWARD would accept a chain of changes (add a field with a default, later drop the default) that breaks reading the oldest data; the tests show the registry refusing exactly that. Two conventions also keep older consumers working when a producer upgrades first: every enum starts with `UNKNOWN`, which is its default, and every added field is optional with a default. A change that cannot follow these rules is a new major version: a new topic and subject, dual publishing during the migration, then the old topic retires.
5. **Checked before merge, enforced by the registry after.** `make schemas-check` rebuilds every committed version of each subject from git history and checks the working tree against them with the reference Apache Avro checker, at the catalogue's level, without any registry. `make schemas-register` sets the level on each subject and registers; the registry refuses incompatible schemas (HTTP 409). The offline checker and Redpanda agree on the tested cases.
6. **Identity, time and de-duplication.** Every event has an `envelope` with `event_id` (a UUID, v7 recommended, created when the event happens and reused by retries and offline replays, so consumers de-duplicate on it), `client_ts` (device clock, used for elapsed and lag time) and `server_ts` (set by Kuizi), both in UTC milliseconds, and pseudonymous UUIDs only: `student_id`, `session_id`, `focus_session_id`.
7. **Privacy by construction.**
   - Every field carries a privacy label in its schema: `none`, `pseudonymous`, `personal` or `sensitive`. The data catalogue says who may read each class.
   - Sensitive fields live only in `AccommodationContext` (time multiplier, untimed, assistive modes), carried only by `item.presented` and `item.answered`, null without the separate accommodation consent. Each event lists who may read them. The check rejects a sensitive field anywhere else, and field names that invite personal data (email, phone, national ID, IP, location, key codes, free text).
   - `tutor.message` carries metadata only: the conversation text stays in the tutor's store under its own access and retention rules, because a learner's free text can hold personal data that cannot be minimised automatically.
   - Raw keystrokes, key codes and screen-reader commands are never recorded (`item.interaction` keeps one event per gesture and only a key count for typing). No IP address, location, device identifier or user-agent string is part of any event.
8. **Retention hints per event** in the catalogue: at most 30 days in Kafka (so copies expire within the 30-day erasure deadline of T018) and at most 24 months raw in the warehouse (T018), less for micro-interactions. The DPO confirms them in the DPIA (T017).
9. **One machine-readable catalogue** (`schemas/events/catalogue.yaml`) holds owner, producer, consumers, sensitive readers, retention and the knowledge-tracing input map. The page `docs/data/event-catalogue.md` is generated from it and from the schemas, and the check fails when they disagree.

## Consequences

- Each new event is a schema file, a catalogue entry and an example; CI runs the checks and tests through the `schemas/` uv project (ADR 0008). The compatibility check needs the full git history in CI (`fetch-depth: 0`); in a shallow clone it only checks the commits it has, and says so.
- T024 builds its TypeScript types from the expanded schemas (`kuizi-schemas expand`); T025 validates incoming JSON against them and applies the same rules as `kuizi_schemas.examples` (identifiers, ranges, required envelope fields), then produces with the registry wire format. Topic creation (partitions, retention) belongs to T025 locally and T021 in the cloud, from the catalogue's values.
- Fifteen topics instead of one. The warehouse joins item events on `presentation_id`; the online path reads `item.answered` alone.
- Accommodation data travels in two topics. Before real learners (the pilot, S12), the product owner and the DPO choose how to restrict it: topic access control plus warehouse column masking (T217), or field-level encryption with the accommodation key (T015, T151), added as a new optional field so the change stays compatible.
- `subject_id` and `track_id` are already optional fields of `ItemContext`, so T033 fills them without a schema change.
- The cloud registry (T021) reuses the same subjects and level; `make schemas-register` takes `SCHEMA_REGISTRY_URL` from the environment.
